# Harness 证据状态与红蓝队规则

> 优先级：高
> 创建：2026-11-10 ｜ 公开版：v5.2.0
> 来源：把竞赛、论文、产品、课程多个工作区各自长出来的验收做法合并成一份共享契约。共同的失败模式是：本地跑通、构建成功、页面存在，被直接写成“已发布”“已验收”。

---

## 核心公式

```text
Agent   = 模型 + 规划 + 记忆 + 工具 + Harness
Harness = 来源守卫 + 实例守卫 + 任务状态 + 团队角色 + 审查 + 验证 + 证据
```

Harness 不规定业务流程，只规定：谁读什么、谁负责什么、什么结果能复用、什么时候必须停下复核。

## 规则 1：执行循环

```text
discover → freeze → preflight → plan → execute → emit → review → verify
                                         ├─ repair → verify
                                         ├─ resume → execute
                                         └─ stop   → 人工决策
```

每个任务至少记录：任务标识、目标路径、来源清单、负责人、当前状态、证据等级、下一步。

## 规则 2：状态阶梯，不压缩成“完成”

| 状态 | 含义 |
|---|---|
| `SOURCE_ONLY` | 只有来源或规则，尚未在本项目复现 |
| `LOCAL_ONLY` | 本地静态检查或本地运行完成 |
| `BUILD_VERIFIED` | 构建、结构或安装包门禁通过 |
| `DEVICE_VERIFIED` | 指定真实设备或目标环境验证通过 |
| `PUBLISHED` / `SUBMITTED` | 有平台回读、提交回执或公开入口证据 |
| `PENDING` / `BLOCKED` / `REJECTED` | 阻塞、待决策或淘汰，并写明原因 |

失败、跳过、待登录、待用户选择、工具不可用，保持原状态。本地、构建、设备、平台、发布分别验收，不能互相替代。

## 规则 3：蓝队、红队、第一性原理席

- **蓝队**：把需求变成可运行的最小闭环，提交候选结果和复跑命令。蓝队不能宣布自己通过。
- **红队**：独立重建问题，查变量与单位是否被偷换、有无数据泄漏或选择性展示、结论能否被另一份输入推翻、“通过”是否只是退出码或页面存在。输出必须包含失败条件、复现方式和影响范围，不能只写“有风险”。
- **第一性原理席**：先回答四件事——要优化或证明的对象是什么；哪些事实来自原始材料或用户确认；哪些假设改变了问题本身；什么最小实验能区分两条路线。

## 规则 4：舰队成立条件

同时满足才开多智能体舰队：任务能拆成互不阻塞的专线；每条专线有独立输入和交付物；至少一个独立验证席；主控有统一状态表；并行节省大于同步成本。最小配置：主控、侦察、构建、验证各 1。

## 规则 5：独立验证不得复用生成逻辑

验证者从输入重新计算或重新打开文件，不调用生成结论时用过的同一个聚合函数。生成者不能当自己的审查者。

## 规则 6：完成门禁

关闭任务前回答：真源和版本是否冻结；每个结论能否回到文件、输出或回执；红队是否尝试推翻过关键结论；哪些仍是 `PENDING`、`LOCAL_ONLY`、`BLOCKED`；新智能体能否只读交接入口就接管。回答不完整，任务保持未关闭。
