# 规则变更审计协议

> 优先级：高
> 创建：2026-08-23 ｜ 公开版：v5.2.0
> 来源：维护者直接下达。AI 判断“这条改进更合理”就直接改主工作流文档，事后无法说明改动是否真的变好。

---

## 触发条件

AI 认为当前工作流、参数或代码策略需要修改，或用户要求采纳一条新规则时，先执行本协议，禁止直接覆盖主工作流文档。

## 执行流程

1. **隔离改动**：一次只测试一条改动。同时想到多条，拆成待验证队列逐条测试，禁止打包。
2. **建立基线**：用当前版本在相同条件下（同一测试用例、同一数据、同一评分脚本）跑一次，记录基线。条件未变时可复用已有基线。
3. **应用并测试**：在与基线完全相同的条件下重测。观测窗口不少于 5 次独立运行，或足以反映稳定性的时长，并说明选择理由。
4. **禁止自我判断**：“我认为更合理”“更符合最佳实践”不是采纳依据。唯一依据是可复现的量化对比。评分本身有随机波动时，先说明如何控制（例如取多次中位数）。
5. **输出审计记录**，写入独立的审计日志，不写进主工作流文档：

```
改动内容：
测试条件是否与基线一致：是 / 否（说明差异）
基线结果：
改动后结果：
差异是否可复现：
结论：【采纳 / 回滚 / 证据不足，延长观测】
```

6. **采纳与回滚**
   - 【采纳】才允许写入主工作流文档。
   - 【回滚】撤销改动，保留记录和失败原因，写入 `negative-results`，防止重复测试已证伪的思路。
   - 【证据不足】不采纳、不回滚，标记为待更长观测。

## 明确禁止

- 用“批判性看待”代替对照测试。批判性判断只决定要不要测，不能代替测试结果。
- 没有基线就评价改动效果。
- 同一窗口测试多条改动后笼统宣布“整体变好了”。
